# PaySim-Fraud-Detection

## Overview

This project builds a machine learning classifier to detect fraudulent transactions on a simulated mobile money platform. It was developed as a live-build data science assessment, with the objective of producing not just a working model, but an honestly evaluated one, together with a clear explanation of which features are trustworthy to use and why. The dataset used is PaySim, a synthetic dataset designed to resemble real mobile money transaction logs from a financial service operating across several African countries. Because financial transaction data is inherently private, PaySim was created as a way to make a realistic, shareable dataset available for fraud detection research without exposing any real customer information.

## The problem being solved

Mobile money platforms process an enormous number of transactions, and only a very small fraction of them are fraudulent. In this dataset, fraud accounts for roughly 0.13% of all transactions, which means a model cannot be judged on accuracy alone. A model that simply predicted not fraud for every single transaction would be correct 99.87% of the time while being completely useless in practice, since it would never catch a single real case of fraud. The real objective of this project was therefore to build a model that could usefully flag suspicious transactions for human review, while being upfront about the trade-off between catching more fraud and generating false alarms.

## Approach

The project follows the CRISP-DM methodology, which structures a data science project into six phases: business understanding, data understanding, data preparation, modelling, evaluation, and deployment. Work began by clearly defining the business objective before any data was touched, framing the model's output as a tool that would feed into a review queue.This framing shaped every later decision, since it meant that missing a genuine fraud case was treated as more costly than generating an unnecessary review.

During data understanding, exploration of the full dataset of 6,362,620 transactions revealed that fraud occurs exclusively within two transaction types, TRANSFER and CASH_OUT, and never appears in the remaining three types, PAYMENT, CASH_IN, and DEBIT. This finding was used to scope the dataset down to only the transaction types where fraud can actually occur, reducing the working dataset to 2,770,409 transactions and raising the fraud rate to approximately 0.30%. This was a deliberate modelling decision rather than a shortcut, since the excluded transaction types carried no information relevant to distinguishing fraud from legitimate activity.

A significant part of the project involved judging which features were genuinely safe and fair to use. The dataset's own documentation warns that several balance-related columns, specifically newbalanceOrig and newbalanceDest, must not be used for fraud detection, because fraudulent transactions are cancelled within the simulation, which distorts these post-transaction balance figures. This warning was treated as authoritative and was additionally cross-checked , by comparing account balances between fraudulent and legitimate transactions. That comparison showed that the pre-transaction balance columns, oldbalanceOrg and oldbalanceDest, carry genuine and legitimate predictive signal, since fraudulent transactions were found to target accounts with higher balances than legitimate transactions on average. These pre-transaction columns were retained, while the post-transaction balance columns were excluded. Two further columns, the customer identifiers nameOrig and nameDest, were also excluded, since they take on a nearly unique value for almost every row and therefore cannot provide any pattern that generalises to new customers. A final column, isFlaggedFraud, records the output of an existing, rule-based system that flags any transfer over 200,000 in value. This column was excluded as a model input because using it would be circular, asking the new model to rely on the output of an older system, and because it was found to flag only 16 transactions across the entire 6.36 million row dataset, meaning it carries very little information.

## Model and evaluation

A logistic regression classifier was selected as the model for this project, trained with class weighting enabled to counteract the severe imbalance between fraudulent and legitimate transactions. Logistic regression was chosen deliberately over more complex alternatives because it produces interpretable coefficients, allowing the direction and relative importance of each feature to be examined directly, and because it provides a credible, well understood baseline. The data was split into training and test sets using a stratified split, which ensures that both the training and test sets contain the same proportion of fraud cases, rather than leaving this to chance in a dataset where the fraud class is already extremely rare.

Because accuracy is not a meaningful metric for a problem this imbalanced, the model was evaluated instead using precision, recall, the F1 score, and two versions of the area under the curve metric, ROC-AUC and PR-AUC. At the default decision threshold of 0.5, the model achieved a recall of approximately 85%, meaning it correctly identified 85 out of every 100 real fraud cases in the test set, while its precision was approximately 3%, meaning that only around 3 out of every 100 transactions it flagged as fraud were actually fraudulent. The ROC-AUC score of 0.95 initially appears very strong, but this metric is measured against the very large population of legitimate transactions and can therefore look misleadingly high even when a model generates a large number of false positives. The PR-AUC score of 0.20 is a stricter and more informative measure under this level of class imbalance, since it is calculated directly against the model's positive predictions rather than the entire dataset. A PR-AUC of 0.20 represents an improvement of roughly sixty seven times over what a random, uninformed classifier would be expected to achieve on this dataset, given that fraud makes up only about 0.3% of transactions after scoping.

## Choosing a decision threshold

Rather than accepting the default threshold of 0.5 without question, several alternative thresholds were tested to make the trade-off between precision and recall explicit. Lower thresholds catch a greater share of fraud but flag a much larger number of transactions overall, while higher thresholds reduce the review workload but allow a larger share of real fraud to go undetected. A threshold of 0.5 was ultimately selected as the operating point for this project, reflecting a judgement that missing a genuine fraud case is generally more costly to the business than the time cost of an unnecessary review, given that the model's output is intended to feed a review queue rather than trigger an automatic block. At this threshold, the model flags approximately 8.4% of all test transactions for review, and catches approximately 85% of the fraud present in the test set.

## Limitations and possible next steps

This project has several acknowledged limitations that would be worth addressing with further time. The train and test sets were split randomly, although in a stratified way, rather than being split by time, and a time based split, which trains on earlier transactions and tests on later ones, would more realistically reflect how this model would perform once deployed. Only a single model, logistic regression, was evaluated, and a tree based model such as Random Forest may be able to capture non-linear relationships in the data that logistic regression cannot. No behavioural features were engineered from the data, such as how frequently a given account typically transacts or how unusual a particular transaction is relative to that account's own history, and such features could plausibly improve precision. Finally, while the documented warning regarding the excluded balance columns was treated as authoritative, a stronger version of this analysis would additionally train a comparison model that includes those columns, in order to empirically demonstrate the scale of the leakage rather than relying on the dataset documentation alone.

## Repository contents

This repository contains the Jupyter notebook used to carry out the full analysis, covering data loading, exploration, feature selection, model training, evaluation, and threshold selection. The raw dataset itself is not included in this repository due to its size, but it is publicly available from Kaggle under the PaySim Synthetic Financial Dataset, and the notebook can be run against a local copy of that file to reproduce every result described above.

## Data source

The dataset used in this project is PaySim, a synthetic financial dataset available on Kaggle, created to simulate mobile money transactions based on a real, anonymised sample of transaction logs from a mobile financial service operating in an African country. Because the dataset is synthetic, the absolute number of fraud cases and their exact characteristics should not be interpreted as representing real world fraud rates, although the overall structure, class imbalance, and behavioural patterns are designed to closely resemble genuine transaction data.
